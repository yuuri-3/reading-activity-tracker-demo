## 1. プロジェクトコンテキスト

### 1-1. システムを通して実現したいこと（ゴール）

- このアプリを使うことで、読書をはじめとした様々なインプット・アウトプットの活動を記録することができ、あとから振り返ることもできる

### 1-2. 想定される利用者

- 向上心が高く、日頃から読書や勉強などでインプットしたり、実際に手を動かしてアウトプットしたりする習慣がついている学生・社会人
- 尚且つ自分の活動を記録してあとから振り返りたい、自分の軌跡を見て自己肯定感を高めたり満足度を高めたい人

#### 1-2-1. 想定されるリテラシーに関する情報

- 普段からスマートフォンを使い慣れており、Instagram などの SNS に慣れ親しんでいる

#### 1-2-2. システム利用に対する抵抗感の度合い

- IT リテラシー自体は高いが、記録をするために無駄な作業や余分なアクションはできるだけ取りたくない（本来やりたい読書などにすぐに取り掛かって集中したい）

##### 補足：リテラシー × 抵抗感による UI 設計の考え方

- リテラシーが低く、抵抗感が高い利用者を想定する場合：
  - 操作手順や次に行うべき行動が明確に分かる UI とする
  - 誘導文や補足説明を適切に配置する
  - 一度に表示する情報量を抑える
- リテラシーが高く、抵抗感が低い利用者を想定する場合：
  - 情報密度を高め、一覧性・効率性を重視する
  - ショートカット的な操作や省略可能な導線を許容する

### 1-3. 想定される利用場所・デバイス

- スマートフォン・PC

### 1-4. 今回のプロトタイプで対象とするストーリー

- 手動で書籍情報を登録したい
- 読書している本一覧から対象の書籍情報を開きたい
- 書籍情報との紐づけ設定等準備等せずとにかく計測を開始したい
- 履歴に対してメモを残したい 例）P.10 まで読んだ
- 計測忘れの時間をあとで登録したい
- 計測したが不要になった履歴を削除したい
- 書籍そのものに紐づくメモを残したい
- キーワードで履歴メモ・書籍メモをまとめて検索したい
- 各書籍にどれくらい時間を掛けているのか振り返りたい

※ UI を生成する際は、上記に記載されたすべてのストーリーが
画面構成や導線として成立するように構造を設計すること。

#### 記載ガイド（人間向け）

※ 以下は人間がストーリーを記載する際のガイドであり、UI 生成時の制約条件ではない。

- 今回のプロトタイプで「実現したい体験の範囲」を列挙する
- 1 行につき 1 ストーリーとし、動詞から書き始める
- UI 構成や画面名、実装方法は書かない
- 詳細な業務ルールや受け入れ条件は含めない
- 未対応のストーリーは記載しない（スコープ外であることを明確にする）

### 1-5. 想定される画面一覧（任意）

- 最初の画面
  - 画面の最初に計測開始ボタンがあり、すぐに計測を開始することができる
    - この導線で計測を開始した場合、計測を終了する際に書籍情報と紐づけることができる
    - 書籍情報とは紐づけず、計測時間と履歴に対するメモだけ保存することも可能
- 履歴一覧画面
  - 過去計測した履歴の一覧を表示
- 書籍一覧
  - 登録されている書籍の情報と、累計計測時間を一覧画面で確認することができる

※ 本項目は任意であり、記載されていない場合はストーリーのみを前提に UI を構成してよい。
※ 記載されている場合は、画面構成の前提として尊重すること。

#### 記載ガイド（人間向け）

- 今回のプロトタイプで想定している画面を一覧で列挙する
- 画面名＋一言程度の簡単な説明に留める
- 画面遷移や詳細な UI 構成までは記載しない

## 2. UI 判断原則（Principles）

UI 判断原則は、1. プロジェクトコンテキストで定義された
利用者のリテラシーおよびシステム利用に対する抵抗感を前提として適用する。

### 基本原則

- 操作の予測可能性を最優先する
- 情報量は必要十分であることを優先する
- ユーザーに不要な判断をさせない（選択肢は最小限にする）

### UX 観点の補足原則（Nielsen の原則を基に再解釈）

- システムの状態や結果は、常にユーザーが把握できるようにする  
  例：処理中であること、完了したこと、失敗したことを画面上で明確に示す

- 同じ意味・同じ目的の操作や情報は、常に同じ表現・振る舞いにする  
  例：同じ種類のボタンやリンクは、画面が変わっても同じ配置・見た目・挙動とする

- エラーは起きにくく設計し、起きた場合でも回復しやすくする  
  例：実行前の確認、入力制限、エラー時に次に取るべき行動を明示する

- ユーザーの記憶に頼らせず、見れば分かる状態を優先する  
  例：入力例の表示、選択肢の明示、過去の入力内容や状態を画面上に残す

- 利用者の熟練度に応じて、操作効率を高める余地を残す  
  例：一括操作、ショートカット的な導線、省略可能な手順を許容する

- 不要な情報や要素を排除し、重要な情報が埋もれないようにする  
  例：装飾目的の要素を追加しない、業務に直接関係しない情報を表示しない

## 3. 共通 UI ルール（コンテキスト非依存）

### 状態管理・挙動

- 通信中は必ずローディングを表示する
- 処理中は操作できない状態を明示する
- 成功時は画面遷移しない
- 失敗時は原因が分かるエラーメッセージを表示する

---

## 5. 文言・トーン

- 簡潔で事実のみを伝える
- 命令形や感情的表現を避ける
- 専門用語・社内用語の使用は許可する

---

## 7. NG 集（やってはいけないこと）

- 使用するコンポーネントや参照すべきファイルが明示されている場合、それらを逸脱する新しい UI パターンを勝手に追加しない
- 装飾目的のアニメーションを追加しない
- 色数を増やさない
- 業務ロジックを推測して実装しない

## 8. マークアップ／構造ルール（Figma Make 出力の HTML/CSS）

この章は、Figma Make が生成する HTML/CSS の構造（マークアップ）に関するルールを定義する。

### 8-1. テキスト（p タグ）

- 改行を含むテキストは 1 つの p 要素の中で改行として表現する（行ごとに p 要素で分割しない）
- p タグになりうるテキストは、不要な div で個別にラップしない

例（OK）

- 1 つの p の中で、`<br>` などで改行を表現する

例（NG）

- 1 行ごとに p タグを分ける
- p 相当のテキストを div で囲って階層を増やす

### 8-2. Auto Layout の再現（Flex / gap）

- Figma の Auto Layout 構造は、HTML 構造として忠実に再現する
- Auto Layout で gap が設定されている場合 は、子要素ごとの margin ではなく 親コンテナの gap で間隔を管理する
- 余計なラッパー要素の追加によって、Auto Layout の階層や間隔の意味が変わらないようにする
