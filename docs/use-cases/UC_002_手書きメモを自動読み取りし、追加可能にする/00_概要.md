# UC_002 手書きメモを自動読み取りし、追加可能にする

このユースケースは、手書きメモの写真からテキストを自動抽出（OCR）し、既存のメモ機能へ素早く追加できるようにするための要件定義です。

## 背景

- 手書きのメモを取るユーザーが、後からアプリに転記する手間を減らしたい。
- 現状はテキスト手入力が中心で、入力コストが高い。

## ゴール（ユーザー視点）

- 手書きメモを撮影（または画像選択）すると、テキスト化され、編集してメモとして保存できる。
- 保存先を「書籍メモ」または「記録メモ」から選べる。
  - 編集時に元画像をサムネイル表示でき、アップロード画像の取り違いがないか確認できる（拡大/ズームは不要）。

## 決定事項

- 追加先は選択式（書籍メモ / 記録メモ）。
- 保存先の選択は直前の選択を記憶し、次回のデフォルトにする。
  - 実装コスト/複雑性を下げるため、記憶は端末ローカル（ブラウザのローカルストレージ等）に保存し、アカウント間/端末間で同期しない。
- 画像読み取り（OCR）は、新規作成時のフローでのみ利用可能とする（既存メモへの追記/編集時には提供しない）。
- OCR 結果は必ず編集画面を経由してから保存する（自動保存はしない）。
- アプリ（サーバ含む）は画像を保持しない（テキストのみを扱う）。
- アプリを通して撮影した写真は、端末ローカルには残るようにしたい。
- MVP の画像入力は「アルバム選択」から開始する（カメラ撮影は後で追加）。
  - 理由: Web 環境ではカメラ権限・起動の挙動差や、撮影画像を端末フォトライブラリへ確実に保存する要件が絡み、初期実装で事故りやすいため。
- 新規作成時に日付+時間を入力でき、メモはその日時で時系列に表示される（過去分のまとめ登録を想定）。
- 日時入力 UI は既存の手動追加（記録の開始/終了日時）と同等の `datetime-local` 入力を再利用する。
- 日時入力のデフォルト値は現在時刻とする。
- 時系列表示・並び替えに使う日時は「メモ内容に対応するユーザー入力日時」を正とする（システム時刻の作成日時は要件としては不要）。
- 日付+時間の入力は入力時点の端末ローカルタイムゾーンを前提とし、表示も入力した日時（=壁時計の日時）を維持する。
- OCR 方式（MVP）は「外部サービスに画像を送って解析し、保存はしない」方針を許容する（ユーザーの同意・注意喚起を前提）。
  - 背景: 個人情報が写る可能性はあるが、オフライン要件はなく、精度も重視したいため。
  - 想定頻度: 月 100 回未満程度。
- OCR 結果の自動整形はコスト優先で最小限に留め、基本はユーザー編集で整える。
- OCR の再試行導線は用意する（低コストな範囲で）。
  - 例: 同じ画像でもう一度実行 / 画像を選び直して再実行
  - 表示方針: 失敗時に限らず、ユーザーが結果に満足しない場合に自分の意思で再アップロード（画像選び直し）できるようにする
  - 再アップロード時は OCR 結果を置き換える（比較・履歴管理はしない）
  - 注意: 外部サービス呼び出し回数が増えるため利用コストは増加する。
- 書籍メモの対象書籍の指定は「検索できる単一選択ドロップダウン」で行う（現在のタグ選択 UI に近い体験だが、複数選択は不可）。
- 書籍の候補数は現時点では 50 冊未満を想定する（将来大幅に増える場合はリニューアルで再検討してよい）。
- 記録メモ（新規記録）作成時のタグは複数選択を許容する。
- 記録メモ（新規記録）作成時、実装コスト/複雑性が大きく増えない範囲で、その場で新規タグ作成も許容する。
- 記録メモ（新規記録）の日時入力はユーザーに単一の日時だけ入力してもらえば OK とする（開始/終了の 2 項目は要求しない）。
- 記録メモ（新規記録）作成では、読書時間（duration）は MVP では入力しない。
- 時系列表示/並び替えは既存の日時フィールドで担保する（実装コスト最小）。
  - 書籍メモ: ユーザー入力の日時を `BookMemo.createdAt` に保存して並び替え
  - 記録メモ（新規記録）: ユーザー入力の単一日時を `ReadingRecord.startTime` / `endTime` に保存して並び替え
- 注意喚起/同意の扱いは、プライバシーポリシーの記載に加えて、初回利用時に短い注意喚起を表示する方針を推奨（最終判断は未決）。
  - 理由: 「写真を外部に送って解析する」ことはユーザーの期待とズレやすく、本文に書くだけだと気づかれない可能性があるため。
  - 注意喚起に含める要素: 外部送信する / 画像は保存しない / 個人情報が写り込まないよう注意

## 対象（関連領域）

- 既存データモデル
  - 書籍メモ: `Book.memos[]`（`BookMemo { id, text, createdAt }`）
  - 記録メモ: `ReadingRecord.memo`（文字列）
- 既存 CRUD/画面
  - 書籍メモ/記録メモの追加・編集導線

## 非ゴール

- OCR エンジンの選定・実装方式の確定（端末内/サーバなど）は、この段階では決めない。
- 画像の保存・共有・ライブラリ管理（アプリ内ギャラリー）機能は作らない。
- OCR 結果の自動整形（要約、箇条書き化、タグ抽出など）は必須要件にしない。

## 未決事項（要件詰めの論点）

- 起動導線（どの画面から開始するか、最短フローは何か）。
- OCR 編集画面の UI 詳細（保存先選択 UI の配置・画面レイアウト等）は後日検討して反映する。
- 新規作成フローへの組み込み方
  - 案 A: 既存の新規作成画面（書籍メモ作成 / 記録作成）に「画像読み取り」オプションを追加
  - 案 B: OCR 専用の新規作成フロー（別画面）を作り、保存先（書籍メモ/記録メモ）へ分岐
  - 判断基準: 既存 UI の崩れにくさ、入力項目（書籍/タグ/日時）の自然な置き場、迷いにくさ
- OCR の入力（複数枚対応、トリミング等の要否）。
  - MVP はアルバム選択のみ。カメラ撮影追加の時期は未決。
- OCR の仕様（言語、精度目標、タイムアウト、再実行）。
- 保存時の挙動（保存前に必ず確認/編集するか、保存後の編集導線）。
- 新規作成フローで必要な入力項目と必須/任意
  - 書籍メモ: 対象書籍
  - 記録メモ: タグ、日時
- 失敗時 UX（ネットワーク不安定、認識失敗、権限拒否）。
- 「端末に写真を残す」の実現方法と制約（ブラウザ/OS 依存）。
