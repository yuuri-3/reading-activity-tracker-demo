# UC-002 要件定義（手書きメモ OCR）

## 1. 用語

- OCR: 画像（手書きメモ）から文字を抽出する処理。
- 書籍メモ: `Book.memos[]` に入るメモ。
- 記録メモ: `ReadingRecord.memo` に入るメモ。

## 2. 想定ユーザー

- 手書きでメモを取り、後でアプリに転記しているユーザー。
- タイピングが負担なユーザー（短時間で残したい）。

## 3. ユーザーフロー（案）

### 3.1 最小フロー（MVP）

前提: 画像読み取り（OCR）は「新規作成」時のみ利用可能。
（= 既存のメモを上書き/追記する機能は対象外。OCR 結果は新規作成の内容として保存する。）

1. 新規作成フローを開始（書籍メモ作成 or 記録メモ作成）
2. 画像を用意する（撮影 or 画像選択）
3. OCR 実行
4. 抽出テキストを編集
5. 保存先を選択（書籍メモ / 記録メモ）
6. 追加情報を入力（書籍メモ: 対象書籍 / 記録メモ: タグ・日時）
7. 保存

### 3.2 保存先の選択

- 追加先は選択式。
- 保存先の選択は直前の選択を記憶し、次回のデフォルトにする。
  - 実装コスト/複雑性を下げるため、記憶は端末ローカル（ブラウザのローカルストレージ等）に保存し、アカウント間/端末間で同期しない。
- 選択 UI の場所（候補）

  - OCR 結果の編集画面で選択
  - または「開始導線」自体を分ける（書籍詳細から入る場合は書籍メモが既定、記録追加から入る場合は記録メモが既定）

  - データ表現（低コスト案）: ユーザーが入力した日時を `BookMemo.createdAt` に格納し、表示・並び替えの根拠にする。

## 4. 機能要件

### 4.1 入力（画像）

- カメラ撮影と、端末内画像の選択の両方を提供できるのが理想。
- MVP は「アルバム選択（端末内画像の選択）」のみで開始する。
  - 理由: Web 環境ではカメラ権限・起動の挙動差や、撮影画像を端末フォトライブラリへ確実に保存する要件が絡み、初期実装で事故りやすいため。
  - 将来: カメラ撮影も追加する。
- 1 回の追加で扱う画像枚数: 未決（まずは 1 枚想定）。
- 画像の前処理（トリミング/回転/補正）: 未決（必要最小から）。

  - データ表現（低コスト案）: ユーザーが入力した単一日時を `ReadingRecord.startTime` と `ReadingRecord.endTime` の両方に格納し、時系列表示・並び替えの根拠にする。
    - `duration` は MVP では `0` を想定（将来、duration 入力時に `endTime` を計算できるようにする）。

### 4.2 OCR

- 日本語の手書きメモを主対象とする（英数字混在の扱いは未決）。
- OCR の完了/失敗がユーザーに明確に分かる。
- OCR 失敗時は、手入力に切り替えられる（最低限）。
- OCR の再試行導線を提供する。
  - ユーザーが結果に満足しない場合に、自分の意思で再アップロード（画像選び直し）して再実行できる
  - （任意）同じ画像でもう一度実行できる
  - 再アップロード後は前回の OCR 結果を置き換える（比較・履歴管理はしない）
  - 注記: 外部サービス呼び出し回数が増えるため、利用コストは増加する

### 4.2.1 OCR 結果の整形（コスト優先）

- 追加コスト（追加 API 呼び出し/追加 AI 処理）をかけない方針とする。
- OCR 結果は原則そのまま表示し、ユーザーが編集して整える。
- 自動整形は最小限に留める（例: 前後の空白トリム、改行コードの正規化、連続改行の抑制など）。
- 改行/箇条書きの「元の見た目」を厳密に再現する要件にはしない。

### 4.3 編集

- OCR 結果は保存前にユーザーが編集できる。
- OCR 結果は必ず編集画面を経由してから保存する（自動保存はしない）。
- 編集画面で「保存先の選択」ができる。
- 編集画面で、元画像のプレビューを表示できる（ユーザーが修正しやすいことを優先）。
- プレビューはサムネイルで十分（アップロード画像の取り違い確認が目的）。拡大/ズームは MVP では不要。

### 4.4 保存

- 書籍メモとして保存する場合
  - 新規作成時に対象書籍を指定できる。
  - 対象書籍の指定 UI は「検索できる単一選択ドロップダウン」を想定（タグ選択 UI のように検索できる体験。ただし複数選択は不可）。
    - 前提: 現時点の書籍数は 50 冊未満を想定し、クライアント側で候補を絞り込めれば十分。
    - 将来、書籍数が大幅に増える場合はリニューアルで再検討してよい。
  - 新規作成時に日付+時間を入力できる（過去分のまとめ登録を想定）。
    - UI は既存の手動追加（記録の開始/終了日時）で使っている `datetime-local` 入力と同等の見た目/操作感を再利用する。
    - デフォルト値は現在時刻とする。
  - 表示・並び替えに使う日時はユーザー入力日時を正とする（システム時刻の作成日時は要件としては不要）。
  - 保存先フィールド: `BookMemo.text`
  - 保存挙動: 対象書籍に「新しい書籍メモ（1 件）」として追加する（既存メモの上書き/追記はしない）
- 記録メモとして保存する場合
  - 新規作成時にタグを指定できる（複数選択可）。
  - タグの指定は検索できる入力（ドロップダウン）を想定する。
  - 既存 UI の延長で実装コスト/複雑性が大きく増えない範囲で、その場で新規タグ作成も許容する。
  - 新規作成時に日付+時間（単一の日時）を入力できる（過去分のまとめ登録を想定）。
    - 開始/終了の 2 項目入力は MVP では要求しない。
    - UI は既存の手動追加（記録の開始/終了日時）で使っている `datetime-local` 入力と同等の見た目/操作感を再利用する。
    - デフォルト値は現在時刻とする。
  - 表示・並び替えに使う日時はユーザー入力日時を正とする（システム時刻の作成日時は要件としては不要）。
  - 読書時間（duration）は MVP では入力しない（将来的に追加できる余地を残す）。
  - 保存先フィールド: `ReadingRecord.memo`
  - 保存挙動: 「新しい記録（1 件）」として作成する（既存記録の上書き/追記はしない）

### 4.5 表示（時系列）

- 書籍メモ/記録メモともに、ユーザーが入力した日時で時系列に表示される。
- 「登録した順」ではなく「入力した日時」で並び替えられること。
- `createdAt` のようなシステム時刻は、表示/並び替えの根拠にしない（互換性・内部用途で保持される可能性はある）。
- タイムゾーンは「入力時点の端末ローカル」を前提とし、表示は入力した日時（壁時計の日時）を維持する（後から別タイムゾーンで閲覧しても変換しない）。

#### 並び替えの担保（既存への影響を最小にする）

- 記録の一覧/集計は既存実装で `startTime` を基準にしているため、OCR 新規作成でも `startTime` を必ず設定する。
- 書籍メモの表示は `BookMemo.createdAt` を基準にしているため、OCR 新規作成でも `createdAt` を必ず設定する。

#### タイムゾーンの補足（未決・低コスト優先）

既存の日時表現や表示実装との整合を優先し、保存形式は既存と同等の文字列（例: ISO 8601）を前提にする。
ただし「閲覧時にタイムゾーンが変わっても壁時計の日時を固定で見せる」を厳密に保証したい場合は、タイムゾーン情報の保存や表示の作り込みが追加で必要になる（将来拡張）。

## 5. 非機能要件

### 5.1 プライバシー/データ保持

- アプリ側（サーバ含む）は画像を保持しない。
- 送信が必要な方式（サーバ OCR 等）を採用する場合でも、画像は永続保存せず、処理後に破棄する方針とする（実現方法は未決）。

### 5.4 OCR 方式（AI を含む）

本ユースケースでの「OCR」は実装方式を限定しない。代表的には次の 2 系統がある。

- 専用 OCR（Vision OCR）: 画像から文字を抽出することに特化したサービス/エンジン。
- 画像理解 AI（例: ChatGPT のようなマルチモーダル AI）: 画像中の文字を読み取り、整形して返すこともできる。

いずれも「画像を外部に送って処理する」場合は、画像を保持しない方針でも“送信は発生する”ため、ユーザーへの説明・同意を必須とする。

MVP 方針（暫定）:

- 精度を重視し、外部サービスに画像を送って解析する方式を許容する（画像は永続保存しない）。
- 個人情報が写り得るため、利用開始時に注意喚起と同意を求める（推奨）。
- オフライン対応は必須にしない。

#### 同意/告知（未決・推奨）

選択肢:

- 案 A: プライバシーポリシーに記載するだけ
  - メリット: 体験がシンプル
  - デメリット: ユーザーが気づかない可能性がある（写真を外部に送って解析することは期待とズレやすい）
- 案 B: 初回利用時に短い注意喚起を表示し、続行で同意扱い（＋プライバシーポリシーへのリンク）
  - メリット: 安心感と説明責任のバランスが良い
  - デメリット: 初回だけ 1 ステップ増える

推奨: 案 B（初回のみ）。最終的な法務/運用判断は別途確認する。

##### 初回注意喚起（文言案・要件）

初回のみ表示し、以降は表示しない。

含める要素:

- 画像を外部サービスに送信して解析する
- 画像は保存しない
- 個人情報が写り込まないよう注意を促す

文言案（1 文）:

> 画像は外部サービスに送信して文字認識します（画像は保存しません）。個人情報が写り込まないようご注意ください。

補足（UI 要件）:

- プライバシーポリシーへのリンクを表示する
- ボタンは「続行」「キャンセル」を想定

### 5.2 端末ローカルへの写真保存

- アプリを通して撮影した写真は、端末ローカル（フォトライブラリ）に残るようにしたい。
- 制約:
  - Web アプリではブラウザ/OS の挙動に依存する可能性がある（自動保存できない場合がある）。
  - 実現方針は「要検討」とし、実装方式決定時に仕様に反映する。

### 5.3 パフォーマンス

- OCR 処理はユーザーが待てる時間に収める（目標値は未決）。

## 6. エラー/例外要件

- カメラ権限拒否: 代替手段（画像選択）を提示する。
- OCR 失敗: 再試行導線を提供する（未決: 自動/手動）。
- ネットワーク失敗（サーバ方式の場合）: 失敗を明示し、復帰可能にする。

## 7. 受け入れ観点（要件レベル）

- 画像からテキスト化し、編集して保存できる。
- 保存先をユーザーが選べる。
- アプリ側に画像が残らない（仕様として明文化され、実装で担保できる）。
