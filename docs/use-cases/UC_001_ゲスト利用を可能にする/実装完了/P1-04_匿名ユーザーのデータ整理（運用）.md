# P1-04 匿名ユーザーのデータ整理（運用）

## ゴール

- link 不可ケースで anon→uid へ移行したあと、古い anon 側のデータ/ユーザーが残る問題を運用として整理する

## 対象

- 運用方針（本ドキュメント）
- （必要になった場合）サーバー側の整理手段（Cloud Functions / バックオフィス等）

## 作業内容

- 既存アカウントへの統合が必要なケース（link 不可）で、サーバー側（Cloud Functions callable）で anon→既存 uid の統合を実行し、anon 側のデータ/ユーザーを削除する
- フロントは環境変数でバックエンド統合を優先し、失敗時のみ従来のクライアント統合フローへフォールバックする
- 統合処理中は UI で全画面ローディングを表示して、待機の不安を軽減する

## 最終結果（採用した運用）

- 原則、link 失敗（既存アカウントに資格情報が紐付いている）時は **Cloud Functions による統合**を実行する
  - Firestore: `users/{anonUid}/{tags|books|records}` → `users/{targetUid}/{tags|books|records}` を **merge（追加のみ）**でコピー
  - コピー後、anon 側のサブコレクション/ユーザードキュメントを削除（匿名っぽい Auth ユーザーのみ削除を試行）
- フロント切替は `VITE_ENABLE_BACKEND_GUEST_MERGE=true`（Vite のためビルド/起動時に固定）
- 統合処理中（ログイン/移行）は書斎で全画面ローディング表示
- 短命チケット（`guestMergeRequests`）は Firestore TTL で自動削除（推奨: `deleteAt` を TTL 対象）

## 現状の整理

- Firestore は `users/{uid}/{tags|books|records}` にデータを保存している
- Google ログイン時は原則 `linkWithPopup` により uid を維持できるため、基本は「移行不要」
- ただし `auth/credential-already-in-use` など「既存アカウントへ統合」ケースでは、anon uid 側のデータが残りうる

## サーバー側での統合（推奨）

Cloud Functions（callable）で anon→ 既存 uid のデータ統合とクリーンアップを行う。

- 追加した関数
  - `prepareGuestMerge`: anon の認証状態で「統合リクエスト（requestId/secret）」を発行（TTL 15 分）
  - `previewGuestMerge`: anon の認証状態で requestId/secret を提示し、移行件数（tags/books/records）を返す
  - `executeGuestMerge`: 既存 uid の認証状態で requestId/secret を提示し、
    `users/{anonUid}/{tags|books|records}` → `users/{targetUid}/{tags|books|records}` を `merge: true` でコピー後、anon 側を削除

補足:

- `functions/` は Admin SDK を使うため、Firestore Rules を迂回する。権限チェックは Functions 内で実施する。
- anon の Auth ユーザー削除は「匿名っぽい（provider 無し & email/phone 無し）」場合のみ試行する。

### Firestore TTL での自動削除（方針 A）

`guestMergeRequests` は「統合処理のための短命チケット（requestId/secret）」なので、
**Firestore の TTL 機能**で期限切れドキュメントを自動削除するのが運用コスト的におすすめです。

- TTL 対象フィールド（推奨）: `deleteAt`（Timestamp）
  - `deleteAt` は「履歴として残してよい期限」です（例: 作成から 7 日）
  - `expiresAt` は「統合リクエストの有効期限（例: 15 分）」として短く保ちます
    - `expiresAt` を長くすると “チケットが使える期間” も伸びてしまうため、役割を分離します

注意:

- TTL 削除はバックグラウンド処理のため、期限ぴったりに即時削除される保証はありません（遅延することがあります）
- `deleteAt` を TTL 対象にすれば **作成から概ね 7 日後に消える**運用にできます
- 過去に作成済みで `deleteAt` が無いドキュメントは TTL 対象にならないため、必要に応じて手動削除 or 追加のバックフィルで対応します

設定手順（Firebase Console）:

1. Firebase Console → Firestore Database を開く
2. TTL（Time to Live）設定へ進む
3. `guestMergeRequests`（コレクショングループ）を選び、TTL フィールドに `deleteAt` を指定して有効化
4. 以後、期限を過ぎたドキュメントは自動で削除されます

### フロントからの切り替え

- 既存の移行フローに対して、環境変数でバックエンド統合を優先できる
  - `VITE_ENABLE_BACKEND_GUEST_MERGE=true`
  - 未デプロイ等で callable が呼べない場合は、従来のクライアント移行フローへフォールバック

  ### デプロイ/設定手順（最終）

  1. Functions をデプロイ
    - `firebase deploy --only functions --project yomzoy`
  2. Firestore TTL を設定（推奨）
    - TTL 対象: `guestMergeRequests`（コレクショングループ）
    - TTL フィールド: `deleteAt`
  3. フロントでバックエンド統合を有効化（常時ON運用）
    - `.env.local` に `VITE_ENABLE_BACKEND_GUEST_MERGE=true`
  4. 動作確認
    - link 成功ケース: uid が維持される（移行無し）
    - link 失敗ケース: 追加のみ統合が走り、完了まで全画面ローディングが表示される

## 非ゴール

## 注意

- クライアント側で anon 側データ/ユーザー削除をやる場合、ネットワーク断などで「移行はできたが削除できない / 逆」になりやすい。
  可能ならサーバー側（Functions）で一連を実行して整合性を担保する。

## 勉強メモ：フロントで頑張っていたこと / バックエンドへ寄せて変わる点

フロントエンド側で“頑張ってたこと”と、バックエンドに寄せることで“何が変わるか”を対比でまとめますね。

**1) これまで（フロントで頑張る方式）にやっていたこと**

- **前提**：ゲスト →Google ログインで `link` ができれば UID が変わらないので問題なし  
  でも `link` ができない（例：すでに同じ Google アカウントが存在）と、**「ゲストの UID」と「統合先 UID」が別**になります。
- そのときフロントは、ざっくりこういう手順を踏んでいました（[src/app/auth/AuthContext.tsx](src/app/auth/AuthContext.tsx) の `confirmFallbackMigration` 付近）:
  - ① **ゲストのまま** Firestore から `users/{anonUid}/tags|books|records` を読み出して、いったんメモリに保持
  - ② “別のアプリ（secondary app）” を内部的に起動して、そこで **Google ログイン**（※ブラウザの制約を避けるために工夫）
  - ③ secondary の認証を使って、統合先の `users/{targetUid}/...` に **「追加コピー（merge）」**していく
  - ④ その後、**認証状態を行ったり来たり**させながら（匿名に戻したり、Google に戻したり）、
    - anon 側の subcollection を削除
    - 最後に anon の Auth ユーザーを削除
    - 最終的に Google ログイン状態へ戻す
- これが大変な理由は、ブラウザ内でやるために
  - **通信が途中で切れる/タブが閉じる**
  - **ログイン状態の切り替えが不安定になりやすい**
  - **削除権限の都合で“いったん匿名に戻る”などが必要**
  - redirect/popup 環境差（iOS やアプリ内ブラウザ）も絡む  
    みたいな“事故りやすい条件”が揃っているからです。

**2) 今回（バックエンドで統合する方式）に変えたことで何が変わる？**
ポイントは「ブラウザでやっていたコピー＆削除の本体を、サーバー側に移した」ことです。

- **変わる点（良くなる点）**

  - **処理が途中で止まりにくい**  
    たとえユーザーが画面を閉じても、サーバー側の処理は最後まで走れる（=中途半端が減る）
  - **権限やログイン状態の行ったり来たりが不要**  
    サーバー側（Admin 権限）で Firestore を操作できるので、クライアントみたいに「匿名に戻って削除」等がいらない
  - **“安全に本人だけが統合できる”形にできる**  
    今回は「ゲスト状態で発行した短命チケット（合言葉）を、Google ログイン後に提示した人だけが統合できる」方式にしたので、成りすましリスクを下げられる

- **変わらない点（注意点）**
  - ユーザー体験としては、ケースによっては引き続き **Google ログインの操作（アカウント選択）は必要**です
  - Firestore のコピーは同じく **“追加コピー（merge）”**が基本（既存データを潰さない方針）

**3) 今回の実装がどこで切り替わる？**

- `VITE_ENABLE_BACKEND_GUEST_MERGE=true` のときだけ、バックエンド統合を優先します（[src/app/auth/AuthContext.tsx](src/app/auth/AuthContext.tsx) 内）
- サーバーが未デプロイ等で呼べない場合は、従来のフロント方式にフォールバックするので、いきなり全部が変わるわけではないです。
