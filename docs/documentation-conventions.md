# ドキュメント運用ルール（refactoring / use-cases）

目的: `docs/refactoring` と `docs/use-cases` 配下のディレクトリ構造・ファイル命名規則を統一し、チケット実装時のブランチ名・PR 名も同じルールで運用できるようにする。

対象:

- `docs/refactoring/**`
- `docs/use-cases/**`

---

## 1. 基本方針

- **ID（ファイル名先頭の識別子）を最優先**: 並び順・検索性を担保するため、ファイル名の先頭は必ず ID を付ける（例: use-cases は `P0-03`、refactoring は `TK-007`）。
- **表記ゆれを防ぐ**: 区切り文字は原則 `_`、ID 内部は既存に合わせて `-` を使用する。
- **ステータスはフォルダで管理**: 完了したチケットは `実装完了/` へ移動、作らない/やらないと決めたチケットは `未実装クローズ/` へ移動する。

---

## 2. use-cases の構造と命名

### 2.1 ディレクトリ構造（標準）

- `docs/use-cases/UC-<NNN>_<ユースケース名>/`
  - `00_概要.md`（必須）
  - `01_要件定義.md`（任意: 仕様が複雑なら作成）
  - `P<優先度>-<NN>_<チケット名>.md`（チケット本体）
  - `実装完了/`（完了チケットの格納先）
  - `未実装クローズ/`（未実装でクローズしたチケットの格納先）

例:

- `docs/use-cases/UC-002_手書きメモを自動読み取りし、追加可能にする/P0-05_OCR編集画面（アルバム選択→OCR→編集）.md`

### 2.2 チケット ID（use-cases）

- 形式: `P<優先度>-<連番>`
  - 優先度は `0/1/2` を推奨（P0 が最優先）
  - 連番は 2 桁ゼロ埋め（例: `01`, `02`, `03`）

### 2.3 ファイル命名規則（use-cases）

- 形式: `P<優先度>-<NN>_<チケット名>.md`
- ルール:
  - 先頭は必ず `P0-01` のような ID
  - ID とタイトルの間は **必ず `_`**
  - 空白は基本使わない

---

## 3. refactoring の構造と命名

### 3.1 ディレクトリ構造（標準）

- `docs/refactoring/RE-<NNN>_<フェーズ名>/`
  - `00_概要.md`（必須）
  - `tech-lead-report.md`（任意）
  - `TK-<NNN>_<チケット名>.md`（チケット本体）
  - `実装完了/`（完了チケットの格納先）
  - `未実装クローズ/`（任意: 今後必要なら作成して運用する）

例:

- `docs/refactoring/RE-001_リファクタリングPhase1/TK-007_アイコン方針統一とlucide移行.md`

### 3.2 チケット ID（refactoring）

- 形式: `TK-<NNN>`
  - `TK-<NNN>` はフェーズ内のチケット連番（3 桁ゼロ埋め）

### 3.3 ファイル命名規則（refactoring）

- 形式: `TK-<NNN>_<チケット名>.md`
- ルール:
  - ID とタイトルの間は **必ず `_`**

---

## 4. チケットドキュメントの本文テンプレ（共通）

- use-cases のテンプレは `docs/use-cases/instruction_template.md` を使用する。
- refactoring は原則同様のセクション構成を推奨（ゴール/対象/受け入れ条件/作業内容/非ゴール/注意）。

運用ルール:

- `Status:` は作業開始時に更新する（例: `⬜ 未着手` → `🚧 進行中` → `✅ 完了`）。
- マージ済みになったら、原則 `実装完了/` にファイルを移動する。

---

## 5. ブランチ名の命名規則（チケット実装用）

### 5.1 目的

- ブランチ一覧で「何のチケットか」が即わかる
- ASCII のみで安全に運用できる（CI/ツール/OS 差分を避ける）

### 5.2 形式（推奨・最小）

- use-cases: `uc-<NNN>/p<優先度>-<NN>`
  - 例: `uc-002/p0-05`
- refactoring: `re-<NNN>/tk-<NNN>`
  - 例: `re-001/tk-007`

補足:

- ブランチ名はツール互換性のため **小文字**（`p0-05`, `tk-007`）で表記する。
- ファイル名/PR 名では英字を **大文字**（`P0-05`, `TK-007`）で表記する。

### 5.3 形式（任意・説明付き）

- 最小形式の末尾に `_<英小文字の短い説明>` を付けてよい
  - 例: `uc-002/p0-05_ocr-edit`
  - 例: `re-001/tk-007_icon-migration`

ルール:

- 小文字英数字とハイフンのみ（`a-z0-9-`）
- スラッシュは 1 回まで（`uc-002/...` のようにグルーピング）

---

## 6. PR 名の命名規則

### 6.1 チケット対応の PR

- 形式: `<大分類ID>_<チケットID>_<チケット名（日本語OK）>`
- use-cases の例:
  - `UC-002_P0-05_OCR編集画面（アルバム選択→OCR→編集）`
- refactoring の例:
  - `RE-001_TK-007_アイコン方針統一とlucide移行`

ルール:

- 区切りは `_`
- refactoring のチケット ID は `TK-007` の形式で表記する

### 6.2 チケット外（雑務/運用）の PR

- 既存ルール通り、ユースケースやチケットに関係ない場合は一度確認を挟ぐ。
