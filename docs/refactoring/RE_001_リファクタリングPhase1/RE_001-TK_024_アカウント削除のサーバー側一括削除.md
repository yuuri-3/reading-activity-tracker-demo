# P1-RE_001-TK_024 アカウント削除のサーバー側一括削除（Admin recursive delete）

このチケットは、「アカウント削除されたユーザーのデータは基本的にすべて削除される」理想状態を、サーバー側（Admin 権限）で担保します。

背景:

- クライアント実装だけだと、削除対象が実装に散らばりやすく、将来サブコレクションやトップレベルコレクションが増えたときに削除漏れが起きやすい。
- Firestore ルール上、ユーザー本人が削除できないトップレベルデータ（例: `guestMergeRequests`）が存在し得る。

## ゴール

- Auth のユーザー削除が発生したら、関連する Firestore データも（ベストエフォートではなく）サーバー側で削除される
- 将来データ構造が増えても「削除漏れ」が起きにくい仕組みにする

## 対象（現状の想定）

- Firestore: `users/{uid}`（配下のサブコレクションを含めて削除）
- Firestore: `guestMergeRequests` のうち、以下を満たすもの
  - `anonUid == uid`
  - または `doneByUid == uid`

## 方針（案）

選択肢 A: Auth 削除トリガーで自動クリーンアップ

- `functions.auth.user().onDelete`（または v2 相当）で uid を受け取り、Admin SDK で削除する
- `admin.firestore().recursiveDelete(db.doc(`users/${uid}`))` でユーザードキュメント配下を一括削除
- `guestMergeRequests` はクエリで該当を検索して削除

メリット:

- クライアント側の削除漏れ・通信失敗に左右されない
- 将来 `users/{uid}` 配下が増えても原則追従不要

デメリット:

- Functions のデプロイが必要
- 失敗時の再実行・監視（ログ/アラート）をどうするか検討が必要

選択肢 B: Callable で「サーバー削除」を明示実行

- クライアントは callable を呼ぶだけにし、削除処理を Functions 側に集約

メリット:

- UI/UX 的に「削除完了」のタイミングを制御しやすい

デメリット:

- callable 失敗時の再試行 UI を作り込む必要がある
- Auth 側のユーザー削除との整合（どちらが先か）を設計する必要がある

## 受け入れ条件

- [ ] Auth ユーザー削除後に、Firestore の `users/{uid}` 配下が残らない
- [ ] `guestMergeRequests` に uid 参照が残らない（対象を明文化する）
- [ ] 大量データ（>500 docs）でも削除が完走する（recursiveDelete / BulkWriter 等で担保）
- [ ] 失敗時にログから追跡できる（uid とエラーを logger に出す）
- [ ] ユーザー向けの完了表示文言が仕様として決まっている（「何が完了した」を含めて誤解が起きない）

## ユーザー向け文言（要仕様決定）

要求:

- 表示文言はシンプルに「アカウントを削除しました」で統一したい

ここで決めること:

- 上記文言が指す「完了」の意味
  - A) Auth（アカウント）削除が完了した（Firestore 側はサーバーで最終的に削除される）
  - B) Auth + Firestore（対象範囲）まで削除完了した
- 失敗時の文言・挙動
  - 例: 「削除に失敗しました」＋再試行導線／サポート案内の有無

備考:

- 「B（全削除完了）」の意味で「削除しました」を出すには、サーバー側処理の完了を待ってから成功を返す設計（callable 等）に寄せる必要がある

## 非ゴール

- 「削除証跡」のために別 DB へ永続保存する（必要になったら別途検討）

## 注意

- これは個人情報削除に近い扱いになるため、監査/規約要件がある場合は要件側で明記する
