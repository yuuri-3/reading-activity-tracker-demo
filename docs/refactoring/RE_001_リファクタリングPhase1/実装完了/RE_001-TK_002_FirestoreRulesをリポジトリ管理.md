# P0-RE_001-TK_002 Firestore Rules をリポジトリ管理にする

このチケットは、Firestore Rules がリポジトリに存在せず、Console 手動変更で属人化しやすい状態を解消します。

## ゴール

- Firestore の認可境界をコードとして固定化し、再現性を上げる
- 誤設定によるデータ漏えい/破壊リスクを下げる

## 対象

- `firebase.json`（rules 参照の設定）
- `firestore.rules`（新規追加）
- 必要に応じて `firestore.indexes.json`
- PROJECT_LOG / DEPLOYMENT_PLAN の記載整合

## 実装状況

Status: ✅ 実装完了（2026-01-12）

## 決定事項（PO 合意）

- 管理者（アプリ内ロール）は設けない（Rules に admin bypass を入れない）
  - Firebase Console 権限（プロジェクト管理者）での閲覧は別レイヤーとして扱う
- ゲスト利用は Firebase Auth の匿名認証（anonymous）を含む前提で許可する
- リスク許容は「安全側で！」（厳しめに倒して問題が出たら修正）
- Console での Rules 直編集は原則禁止（例外運用を作らない）
- Rules を変更したときだけ PO が手動でデプロイする

## 運用案（推奨）

- 反映コマンド（Rules 変更時のみ）: `firebase deploy --only firestore:rules`
- ロールバック方法: 直前コミットへ revert して同じコマンドで再デプロイ
- Console 直編集が必要な緊急事態が起きた場合は、まず「リポジトリ経由での revert/deploy」を優先する

## ロールバックの判断基準（PO 向け）

「どれくらい早く戻したいか」は、次のどれを守りたいかで決めます。

- 最優先（推奨）: 主要機能が使えない/データ保存できない（= 即ロールバック）
- 次点: 一部ユーザーだけ失敗するが回避策がある（= 修正を優先するか、状況次第でロールバック）
- 低: 見た目や軽微な挙動差（= まず修正）

目安としては「主要機能が止まったら 30〜60 分以内に戻せる」運用を目標にする（revert + ルール再デプロイ）。

## 作業内容

### 1) 現行 Rules を確定する（最優先）

- Firebase Console に入っている現行 Rules を取得し、[firestore.rules](firestore.rules) に貼り付ける
  - Console: Firestore Database → Rules → ルール全文をコピー
  - 原則: まずは「現行と同一内容をスナップショットとしてコミット」し、見直し（挙動変更）は別チケット
  - 注意: [firestore.rules](firestore.rules) のテンプレート（deny all）のままデプロイすると既存機能が壊れる

### 2) `firebase.json` から Rules/Indexes を参照する

- [firebase.json](firebase.json) に Firestore の参照設定を追加する
  - rules: [firestore.rules](firestore.rules)
  - indexes: [firestore.indexes.json](firestore.indexes.json)

### 3) ローカルで最低限の動作確認

- 受け入れ条件の「検証観点（最低限）」を、ログイン/匿名で確認する
- 可能なら Rules のスモークテストで機械的に確認する（推奨）
  - macOS: `npm run test:rules:mac`（Firestore Emulator のために Java 21+ が必要）
  - その他: `npm run test:rules`

### 4) 本番へ反映（Rules 変更時のみ）

- PO が手動で反映する: `firebase deploy --only firestore:rules`
- ロールバックは revert + 再デプロイ

### 5) ドキュメント整合

- [DEPLOYMENT_PLAN.md](DEPLOYMENT_PLAN.md) / [PROJECT_LOG.md](PROJECT_LOG.md) に「Rules はリポジトリ管理」「反映手順」を明記

## 非ゴール

- allowlist（メール/UID）などの運用ポリシー変更（必要なら別チケット）

## 注意

- Functions が扱うデータ（例: guestMergeRequests）も含め、意図した read/write 範囲か要確認
