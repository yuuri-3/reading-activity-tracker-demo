# P1-TK-027 検索（部分一致）の方針決定

このチケットは、記録画面/本棚画面で必要になる「部分一致検索 + 絞り込み + ソート」を、Firestore の制約を踏まえて現実的に成立させるための方針を決める。

> 背景: TK-011 で BookMemo をサブコレクション化すると、検索対象が `books/{bookId}/memos/*` に移動する。
> Firestore はサーバー側の部分一致検索ができないため、検索の実現方法を決めないと UX と性能がブレやすい。

## まずこれだけ（結論）

- 記録画面: 一覧は「月単位（当月）」をデフォルトにし、前月/翌月へ移動できる
- キーワード検索: まずは「表示中（当月）の一覧」だけを対象に、アプリ内（`includes` 相当）で部分一致する
- 絞り込み: 日時（= 月）での絞り込みは Firestore の range query で実現し、ラベル（タグ）は追加フィルタとして段階導入する
- 将来: 全期間検索や横断検索（書籍メモまで含める）は将来拡張として別途検討する

## 実装状況

Status: ⬜ 未着手

## ゴール

- PdM が期待する検索体験（何を・どの画面で・どの程度の精度/速度で）を言語化できている
- Firestore の制約に合う実装方針（段階導入含む）が決まっている
- TK-011（Timestamp 化 + サブコレ化）と矛盾しないデータモデルの補足（必要なら denormalize）を決められている

## 決定事項（方針）

- 決定: 外部検索は導入しない（当面ユーザーは増えない、運用を増やさない）
- 決定: 検索品質の定義は「現状の検索体験が継続できること」とする
  - 具体: キーワードで、ラベル（タグ名）・記録メモ・書籍メモ本文が部分一致でヒットし、検索結果として表示される
- 決定: 部分一致の要件は「日本語の単純な部分一致」で OK（高度な形態素解析やランキングは不要）
- 決定: 部分一致判定はアプリ内で行う（`includes` 相当）
  - 前処理: クエリ文字列と対象文字列は同じ正規化を通す（例: `normalize("NFKC")` + `toLowerCase()`）
- 決定: Firestore 側に全文検索用インデックス（n-gram 等）は最初は持たない
- 決定: 記録画面の一覧は「月単位（当月）」をデフォルト表示にする
- 決定: 記録画面は前月/翌月（および今月へ戻る）に移動できる UI を持つ
- 決定: キーワード検索は「表示中（月単位）のレコード一覧」を対象にする（全期間は将来）
- 決定: 月単位の範囲判定は `startTime` を基準にする
- 想定: 当面のデータ規模は「1 ユーザーあたり数千件程度」を想定（これを超えて破綻し始めたら選択肢 B を検討）

## 検索要件（候補・未確定）

### 記録画面

- 一覧: 月単位（当月）。前月/翌月に移動できる
- キーワード検索: 表示中の記録（レコード）のみを対象に部分一致
- 絞り込み: 日時（= 月） / ラベル（タグ）

補足（PdM からの前提）

- キーワードでメモを絞り込むのはメイン体験なので、初期段階から担保したい
- まずは月単位表示の範囲でキーワード検索ができればよい（全期間は将来対応）

### 本棚画面

- 絞り込み: 書籍名
- ソート: 最終記録日時
- 検索: 書籍メモから部分一致

## 現状（参考）

- アプリ内で取得済みのデータに対して、`includes` による部分一致を行っている（クライアント側フィルタ）。
- TK-011 により BookMemo がサブコレ化すると、「全書籍メモ」を検索するには `collectionGroup("memos")` 等での取得設計が必要になる。

## Firestore の制約（重要）

- Firestore はサーバー側での文字列「部分一致検索（contains）」が基本できない。
- 大量件数を「全件購読 → アプリ内で `includes`」すると、通信量/描画/メモリが先に詰まりやすい。
- `array-contains-any` 等には上限があり、検索用トークン方式にも制約がある（誤検知の後段フィルタがほぼ必須）。

このため「全期間」かつ「部分一致」を Firestore クエリだけで完結させることはできない。
本プロダクトでは当面、月単位で取得した一覧に対してクライアント側 `includes` で部分一致する。

## 選択肢

### 選択肢 A: 絞り込みは Firestore、部分一致はアプリ内（まずはこれ）

- 方針
  - 日時レンジ / タグ / 書籍（ID）などは Firestore クエリで絞る
  - 取得できた候補集合に対して、アプリ内で `includes` による部分一致を行う
- 具体案
  - 記録: `records` を `createdAt`（または `startTime`）で range 絞り込みし、タグ/書籍で追加フィルタ
  - 書籍メモ: `collectionGroup("memos")` を `createdAt` で range 絞り込みし、必要なら `bookId` フィールドで絞り込み
- メリット
  - 外部サービス不要・実装が比較的軽い
  - 日本語でも「単純な部分一致」なら期待通り動く
- デメリット
  - 期間指定なしの全件検索は重くなりやすい（UI で制約を設ける必要が出る）

当面の想定規模（数千件）であれば、A を基本方針として「月単位で取得 → 表示中だけ検索」を最初の着地点にする。

### 選択肢 B: Firestore に検索用トークン（n-gram 等）を持つ

- 方針
  - `memoSearchTokens: string[]` のような検索補助フィールドを持ち、`array-contains-any` で候補集合を絞る
  - その後、アプリ内で最終的に `includes` で真偽判定（誤検知除去）
- メリット
  - 外部サービス不要で「ある程度の部分一致」を高速化できる
- デメリット
  - 生成ルール/上限/更新漏れなど、保守コストが上がる
  - Firestore のクエリ制約（上限や複合インデックス）に合わせた設計が必要

（将来案）検索体験が破綻し始めたら、検索用トークン（n-gram 等）や検索用インデックスコレクションの導入を検討する。

### 選択肢 C: 外部の全文検索サービスを導入

- 方針
  - Algolia / Meilisearch / Typesense 等の検索エンジンにインデックス同期し、検索はそちらに任せる
- メリット
  - 検索体験（部分一致・関連度・速度・ランキング）が最も良い
- デメリット
  - 運用/コスト/同期の仕組み（Cloud Functions 等）が増える

## 実装方針（推奨）

### 1) 記録画面: 月単位の一覧 + 月移動

- クエリ: `records` を対象に、表示中の月の範囲で range query
  - 例: `startTime` で `>= 月初` かつ `< 翌月月初`
  - ソート: `orderBy(startTime, "desc")`
- UI: 前月/翌月ボタン + 今月に戻るボタン（または月ピッカー）

### 2) キーワード検索: 表示中（月単位）の一覧だけを対象

- 検索開始条件: 検索欄にキーワードが入ったら即フィルタ（表示中データのみ）
- 判定: `normalize("NFKC")` + `toLowerCase()` の後に `includes`

### 3) 将来拡張（別途）

- 全期間検索（段階的ロード + キャンセル + 途中結果）
- 横断検索の拡張（書籍タイトル/書籍メモ/タグ名まで含める範囲拡張）
- 速度が必要になったら検索トークン/インデックス（選択肢 B）

## データモデルへの影響（TK-011 との接点）

- BookMemo ドキュメントに `bookId` を冗長に持たせるか？
  - 目的: `collectionGroup("memos")` で「特定の書籍だけ」をサーバー側で絞るため
  - 代替: 取得後にアプリ側で `bookId` をフィルタ（ただし取得量が増える）
- Book ドキュメントに `lastRecordAt` を持たせるか？
  - 目的: 本棚画面で「最終記録日時」でサーバー側ソートしたい場合
  - 代替: 現状のように records を参照してアプリ側で算出（データ量が増えると重くなる）

追加検討

- BookMemo サブコレ化後の「全書籍メモ横断の取得方法」を決める必要がある
  - 例: `collectionGroup("memos")` でページング取得（全期間検索時は特に）

## 受け入れ条件（案）

- [ ] 記録画面の一覧が月単位（当月）で表示され、前月/翌月（および今月へ戻る）に移動できる
- [ ] 記録画面で「表示中（月単位）の記録メモ」を部分一致検索できる
- [ ] 記録画面で日時（= 月）の絞り込みが Firestore query（`startTime` 基準）で成立している
- [ ] 本棚画面で書籍名で絞り込みできる
- [ ] 本棚画面で最終記録日時でソートできる（サーバー側/クライアント側のどちらかを明記）
- [ ] 大量データでも破綻しないための制約（期間デフォルト等）が仕様として明記されている

## 未決事項（PdM に確認したい）

会話で前提が固まったため、本チケットとしては以下を決定とする。

- 決定: 当面、キーワード検索の対象は「表示中（月単位）の記録一覧」に限定する（全期間検索は将来対応）
- 決定: 検索対象は以下を含める
  - 書籍: タイトル（必要なら著者も同様に対象へ）
  - 書籍メモ: 本文
  - 記録: 記録メモ本文
  - ラベル: タグ名（タグ自体の検索、および結果の絞り込みに利用）
- 決定: 部分一致の期待値
  - 日本語: 単純な部分一致で OK（読みの揺れ/同義語/ランキングは非対応）
  - 文字の揺れ: 全角半角・英字大小は正規化で吸収（`normalize("NFKC")` + `toLowerCase()` を想定）
