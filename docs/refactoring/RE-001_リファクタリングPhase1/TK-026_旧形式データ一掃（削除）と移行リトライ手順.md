## TL;DR（PdM 向け）

- Firestore の旧形式データ（旧 `books.memos[]` 配列）を削除し、保守負債を減らす
- 実施前に Firestore を **GCS に export** してバックアップする（バックアップは UID 単位では絞れず、プロジェクト全体）
- 削除は **特定 UID のみ**を対象にして実行する（まず 1 UID で試す）
- 失敗時は export を **import して復元**し、必要ならバックフィルを修正して再移行する

## 方針（結論）

- **着手 OK**: TK-011 の「新形式のみ表示（旧形式フォールバック無し）」と「移行漏れブロック（`migrationIssues`）」が実装済みのため、旧形式を削除してもアプリが旧形式へ戻ることはない。
- **ただし前提必須**: 旧 `books.memos[]` を削除すると、バックフィル修正による「旧配列からの再移行」ができなくなるため、削除前に **バックアップ/復元手順を確立**してから実施する。

#### バックアップ方法（推奨）

Firestore の export/import は「プロジェクト全体」を対象にするため、**実施中は書き込みが止まっていること**が前提。

重要: Firestore のロケーションが `asia-northeast1` のため、**export 先の GCS バケットも `asia-northeast1` に合わせる**（ロケーション不一致だと export/import が失敗することがある）。

補足: すでに `gcf-v2-*` などのバケットが存在することがある

- これらは Cloud Functions / Cloud Build 等が内部的に作る「運用バケット」のことが多い
- **バックアップ用途での流用は非推奨**（用途が分かりづらく、将来の運用事故の元になる）
- Firestore export 用には、基本 **バックアップ専用バケット**（または専用プレフィックス）を用意する

このチケットでは、方法 A（gcloud）で確定。

## リトライ手順（バックフィル再実行）

#### リトライの考え方（重要）

- 旧 `books.memos[]` を削除すると「旧配列からの再移行」はできない
- よって、削除後に問題が見つかった場合は **バックアップを復元してから** 再移行する（またはサブコレを正として修正する）

実施フロー:

1. import で Firestore を削除前の状態へ戻す
2. 原因切り分け（アプリ不具合/バックフィル不具合/データ不整合）
3. 必要ならバックフィル（TK-011）を修正して再実行
4. 失敗 0・表示/検索 OK を確認
5. 必要なら TK-026 の削除を再実施

## バックアップ/復元

#### 削除後に問題が発覚した場合の復旧フロー

1. 削除前バックアップから Firestore を復元
2. バックフィル（TK-011）を修正して再実行
3. 失敗 0・表示/検索 OK を確認
4. 必要なら TK-026 の削除を再実施

- バックアップ取得（削除前に必須）
- 復元 → 再移行の手順（削除後に問題発覚した場合）
