# TK-008 ルーティングを切り出し、ユニットテストを追加する

このチケットは、`App.tsx` に密集しているルーティング処理を小さなモジュールに切り出し、変更耐性を上げます。

## ゴール

- ルート解析/生成が `App.tsx` から分離され、見通しが良くなる
- ルート解析の境界条件（basePath/末尾スラッシュ等）をテストで固定できる

## 対象

- 現状のルーティング実装: [src/app/App.tsx](../../../src/app/App.tsx)
- 既存ユーティリティ: [src/app/utils/navigation.ts](../../../src/app/utils/navigation.ts)
- 新規（案）: `src/app/utils/router.ts`（parse/generate を集約）
- テスト: Vitest（`src/app/utils/router.test.ts` など）

## 現状の挙動（固定したい仕様）

現状は [src/app/App.tsx](../../../src/app/App.tsx) 内で、次の仕様になっています。

- URL は `window.location.pathname` のみを解析対象にする（query/hash は解析しない）
- URL 生成は `toPathname()` で pathname を生成し、`joinWithBase()` で base（`import.meta.env.BASE_URL`）を付与する
- ページ切り替え時の `pushState` は `window.location.search` を **維持する**（現状仕様）
- 未知のパスは `home` にフォールバックする
- `/ocr` は feature flag（`isOcrHandwrittenMemoEnabled()`）が ON のときのみ有効

上記を「リファクタ後も壊さない」前提で、型とテストで固定します。

- 理由: 今回はリファクタが目的のため、挙動変更リスクを最小化する
- 補足: 将来「検索条件を URL に含めて共有/ブックマークしたい」要件が出たら、別チケットで URL 設計を見直す

## 作業内容

### 1) API 設計

### 3) テスト
